# 目录与解析器架构

本文档说明 `watermark-backend` 当前的后端目录边界，以及两套解析器如何共存和切换。

## 后台管理系统

- `internal/admin/web/`
  - 后台管理系统的 Web 前端资源。
  - 目前使用 Go `embed` 打包 HTML 模板，后续如果改成独立前端工程，可优先从这里拆出。
- `internal/server/admin_*.go`
  - 后台管理系统后端接口，包括登录鉴权、首页数据、结果库、测试样本、运行设置、任务日志等。
- `internal/server/main.go`
  - 统一注册开放 API、后台页面、后台 API 和任务接口。

当前阶段先完成“后台 Web 前端资源”和“服务端业务逻辑”的目录分离。后续后台功能继续扩大时，可以逐步把 `internal/server/admin_*.go` 迁移到 `internal/admin/backend/`，由 `internal/server` 只负责路由装配。

## 两套解析器

- `internal/parsers/native/`
  - 原生 Go 解析器。
  - 由当前项目长期维护，适合高频平台、缓存命中、可控规则和定制化输出。
- `internal/parsers/universal/`
  - 通用桥接解析器。
  - 负责调用 Python bridge，并复用 `videodl` / `musicdl` 的平台适配能力。
- `bridges/universal/python/bridge.py`
  - Python 桥接脚本。
  - 对接 `CharlesPikachu/videodl` 和 `CharlesPikachu/musicdl`，再转换成与主项目一致的解析 JSON。

后台“运行设置”支持：

- `parserEngine=native`：优先使用原生 Go 解析器。
- `parserEngine=universal`：优先使用通用桥接解析器。
- `parserFallbackEnabled=true`：主解析器失败后自动尝试另一套解析器。

## 上游源码

生产镜像构建时会拉取：

- `https://github.com/CharlesPikachu/videodl`
- `https://github.com/CharlesPikachu/musicdl`

本地开发可执行：

```powershell
.\scripts\sync-universal-parser.ps1
```

或：

```bash
./scripts/sync-universal-parser.sh
```

默认同步到 `third_party/CharlesPikachu/`，该目录不进入 Docker build context，也不提交到仓库。

## 解析组件更新中心

后台管理系统提供“组件更新”页面，用于检查和更新解析相关组件：

- `yt-dlp`：更新到 `/app/tools/venv/bin/yt-dlp`，成功后自动写入运行设置。
- `videodl`：更新到 `/app/tools/CharlesPikachu/videodl`，成功后自动写入运行设置。
- `musicdl`：更新到 `/app/tools/CharlesPikachu/musicdl`，成功后自动写入运行设置。
- `m3u8dl`：当前为预留项，生产 m3u8 合并仍由后端和 `ffmpeg` 完成。

生产环境必须把 `/app/tools` 映射到持久化目录：

```text
/vol1/1000/Configs/watermark-backend/tools:/app/tools
```

组件更新会写入：

```text
/app/tools/venv/
/app/tools/CharlesPikachu/
/app/tools/update-logs/
```

更新请求会立即返回“任务已启动”，实际更新在后端后台执行，管理页通过自动刷新查看 `running` 状态、版本、路径和更新日志。Python venv 使用 `--system-site-packages`，避免源码组件热更新时在持久化目录里重复安装整套依赖。

自动更新默认关闭。建议生产策略：

- `yt-dlp` 可开启自动更新。
- `videodl` / `musicdl` 默认只手动更新，并在更新后运行平台样本测试。
- `ffmpeg` 跟随 Docker 镜像，不在后台热更新。
