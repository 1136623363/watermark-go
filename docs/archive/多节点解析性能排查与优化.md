# 多节点解析性能排查与优化

## 背景

平台能力测试接入 worker 节点后，测试结果出现“多节点总耗时没有下降，甚至略慢”的情况。子节点已经配置代理后，网络不可达类错误会减少，但多节点性能仍取决于调度方式、节点能力一致性和长尾任务控制。

## 已确认的核心原因

1. 当前平台能力测试使用全局并发，而不是按节点扩容。
   - 单节点默认并发为 3。
   - 两节点时仍然是全局并发 3，只是任务被分配到不同节点。
   - 这种情况下不会形成 `gateway 3 + worker 3` 的吞吐提升。

2. 当前任务分配是静态轮询。
   - 逻辑是按样本序号选择节点，例如第 1 个给主节点，第 2 个给 worker。
   - 平台样本耗时差异很大，部分样本 1 秒内结束，部分样本会等待 15 秒、60 秒甚至更久。
   - 静态轮询容易把长尾任务压到某个节点，最终总耗时被最慢节点拖住。

3. 平台能力测试会绕过缓存。
   - 测试使用真实解析结果，绕过成功缓存和失败缓存。
   - 这能反映真实能力，但也意味着每次测试都会产生真实网络、解析器和超时成本。

4. 节点能力可能不完全一致。
   - 代理只是其中一项。
   - 还需要确认 parser fallback、yt-dlp、videodl、musicdl、Chrome、cookies、DNS、超时配置是否一致。

5. 长尾失败样本会吞掉多节点收益。
   - `universal parser timeout after 1m0s`
   - `yt-dlp timeout`
   - 部分音乐平台 15 秒超时
   - 如果长尾任务没有被动态均衡，多节点也会被尾部任务拖慢。

## 排查步骤

1. 确认集群节点基础状态。
   - 后台集群页面中主节点和 worker 都应为健康。
   - worker 的 MySQL、Redis、工具链状态应正常。
   - worker 的节点角色应为 `worker`，主节点应为 `gateway`。

2. 对比主节点与 worker 运行设置。
   - `outboundProxy`
   - `parserFallbackEnabled`
   - `parserEngine`
   - `ytdlpTimeoutSeconds`
   - `universalParserTimeoutSeconds`
   - `universalParserMusicDLTimeoutSeconds`
   - `universalParserVideoDLPath`
   - `universalParserMusicDLPath`

3. 对比工具链能力。
   - `yt-dlp` 是否存在，版本是否一致。
   - `ffmpeg` 是否存在。
   - `videodl/musicdl` 目录是否存在。
   - 需要浏览器的解析器是否能找到 Chrome/Chromium。

4. 用同一批样本做对比。
   - 单节点模式：调度模式设为 `local`。
   - 多节点模式：调度模式设为 `all`。
   - 两次测试使用相同样本、相同超时、相同代理和相同 fallback 设置。
   - 记录总耗时、成功数、失败数、节点分布和长尾任务。

5. 单独观察长尾任务。
   - 统计超过 15 秒、30 秒、60 秒的样本。
   - 如果总耗时主要由少数长尾任务决定，应优先优化调度和测试超时。

## 实现计划

### 第一阶段：调度器修复

目标：让多节点测试真正吃到多节点吞吐，同时减少长尾不均衡。

1. 将静态轮询改为动态任务队列。
   - 每个节点启动固定数量的测试 worker。
   - 哪个节点先空闲，哪个节点取下一条样本。
   - 快节点自然承担更多任务，慢节点不会固定拖住一半样本。

2. 将测试并发解释为“单节点并发数”。
   - 例如配置为 3，两个节点时理论总并发为 6。
   - 这样多节点才有吞吐提升。
   - 后台文案后续应明确为“单节点测试并发数”。

3. 同步改造两种测试入口。
   - 后台常规平台能力测试。
   - 临时样本导入测试。

### 第二阶段：配置一致性

目标：避免 worker 因配置缺失导致成功率下降。

1. Jenkins 部署时保留或写入 worker 的代理配置。
2. worker 默认开启与主节点一致的 parser fallback。
3. 集群页面展示节点 parser/fallback/proxy/tool 状态差异。

### 第三阶段：长尾治理

目标：减少能力测试被少量慢样本拖死。

1. 平台能力测试使用独立超时策略。
2. 对明显不可用的平台快速失败。
3. 失败时记录失败分类，例如 network、unsupported、timeout、missing_media。

### 第四阶段：高级调度

目标：让节点调度更智能。

1. 按节点历史耗时和成功率加权。
2. 对平台做节点亲和性。
3. worker 失败后可选择换节点重试一次。
4. 自动建议禁用成功率低或长时间超时的节点。

## 当前优先级

本轮先实现第一阶段：动态任务队列和单节点并发调度。<br>
配置一致性、长尾治理和高级调度后续分批实现。
